---

# 1. 논문 개요

이 논문은 기존 **LLM-as-a-Judge** 방식의 한계를 극복하기 위해 등장한 **Agent-as-a-Judge** 개념을 체계적으로 정리한 Survey 논문이다.

기존 방식은 LLM이 단일 추론으로 응답 품질을 평가하는 구조였다면, Agent-as-a-Judge는 다음 능력을 포함한다.

- 계획 수립
- 도구 사용
- 외부 검증
- 메모리 활용
- 다중 에이전트 협업
- 실행 기반 평가

즉, 단순히 텍스트를 보고 점수를 매기는 평가자가 아니라, 실제로 탐색하고 검증하고 판단하는 **에이전트형 평가 시스템**으로 발전한다.

---

# 2. 기존 LLM-as-a-Judge의 한계

## 2.1 편향 문제

LLM Judge는 다음과 같은 편향을 가질 수 있다.

- 장황한 답변 선호
- 자신과 유사한 스타일 선호
- 특정 표현 패턴 선호
- 실제 정확성보다 그럴듯함 선호

이로 인해 실제로 더 좋은 답변이 아니라 LLM이 선호하는 스타일의 답변이 높은 평가를 받을 수 있다.

---

## 2.2 검증 불가능성

기존 LLM Judge는 대부분 텍스트만 보고 평가한다.

하지만 실제 시스템에서는 다음 검증이 필요하다.

- 코드 실행 결과 확인
- DB 상태 검증
- API 호출 결과 확인
- 로그 기반 원인 검증
- 웹 검색 기반 사실 확인
- 파일 및 문서 기반 근거 확인

LLM-as-a-Judge는 이러한 실행 기반 검증을 직접 수행하지 못한다.

---

## 2.3 단일 추론의 한계

복잡한 태스크는 여러 기준으로 평가되어야 한다.

예를 들어:

- 정확성
- 완전성
- 안전성
- 논리성
- 효율성
- 사용자 의도 충족 여부
- 근거의 신뢰성

기존 단일 추론 방식은 이러한 복합 평가를 한 번에 처리하려 하기 때문에 평가 품질이 불안정해질 수 있다.

---

# 3. Agent-as-a-Judge 정의

Agent-as-a-Judge는 다음과 같이 정의할 수 있다.

> 계획, 도구 사용, 메모리, 협업, 외부 검증을 통해 실제 검증 가능한 평가를 수행하는 에이전트 기반 평가자

---

# 4. LLM-as-a-Judge와 Agent-as-a-Judge 비교

| 항목 | LLM-as-a-Judge | Agent-as-a-Judge |
|---|---|---|
| 평가 방식 | 단일 추론 | 다단계 평가 |
| 외부 도구 사용 | 제한적 또는 없음 | 가능 |
| 검증 방식 | 언어 패턴 기반 | 실행 및 증거 기반 |
| 메모리 | 없음 또는 제한적 | 가능 |
| 협업 | 단일 모델 중심 | 다중 에이전트 가능 |
| 평가 깊이 | 얕음 | 깊음 |
| 적응성 | 낮음 | 높음 |
| 설명 가능성 | 제한적 | 근거 기반 설명 가능 |

---

# 5. Agent-as-a-Judge 발전 단계

## 5.1 Procedural Agent-as-a-Judge

초기 형태의 Agent-as-a-Judge이다.

특징:

- 고정된 평가 워크플로우
- 사전에 정의된 평가 절차
- 규칙 기반 흐름
- 재현성이 높음

예시:

```text
1. 평가 기준 생성
2. 항목별 평가
3. 점수 계산
4. 최종 결과 생성
```

장점:

- 구현이 단순함
- 운영 안정성이 높음
- 평가 결과 재현이 쉬움

단점:

- 새로운 상황에 유연하게 대응하기 어려움

---

## 5.2 Reactive Agent-as-a-Judge

중간 단계의 형태이다.

특징:

- 중간 결과에 따라 행동 변경
- 외부 도구 호출 가능
- 조건 기반 분기 수행
- 태스크 유형에 따른 평가 전략 변경

예시:

```text
코드가 포함됨 → 코드 실행 도구 사용
수학 문제가 포함됨 → 계산기 사용
사실 검증 필요 → 웹 검색 수행
로그 분석 필요 → 로그 분석 도구 사용
```

---

## 5.3 Self-Evolving Agent-as-a-Judge

가장 발전된 형태이다.

특징:

- 평가 기준을 스스로 개선
- 평가 실패 패턴을 메모리에 저장
- Rubric 자동 생성
- 자기 평가 및 자기 개선 가능

다만 운영 안정성, 보안, 평가 기준 오염 문제를 해결해야 한다.

---

# 6. 핵심 방법론

## 6.1 Multi-Agent Collaboration

여러 평가 에이전트가 역할을 나누어 평가한다.

예시:

- 사실 검증 담당
- 안전성 평가 담당
- 논리성 평가 담당
- 코드 실행 담당
- 최종 판단 담당

효과:

- 편향 감소
- 다양한 관점 확보
- 평가 안정성 향상
- 복잡한 태스크 대응력 증가

---

## 6.2 Planning

복잡한 평가를 단계별로 분해한다.

예시:

```text
1. 평가 목표 분석
2. 평가 기준 생성
3. 필요한 도구 선택
4. 근거 수집
5. 항목별 평가
6. 최종 통합
```

---

## 6.3 Tool Integration

Agent가 실제 도구를 사용하여 검증한다.

사용 가능한 도구:

- 웹 검색
- 코드 실행기
- 계산기
- 데이터베이스 조회
- 로그 분석기
- 파일 리더
- 브라우저
- API 호출기

핵심은 “그럴듯함”이 아니라 “검증 가능성”이다.

---

## 6.4 Memory & Personalization

이전 평가 결과와 실패 패턴을 기억한다.

활용 예시:

- 반복되는 환각 패턴 감지
- 사용자별 평가 기준 반영
- 이전 평가 이력 기반 일관성 확보
- 장기 작업에서 문맥 유지

---

## 6.5 Optimization

Judge 자체를 개선한다.

예시:

- 평가 결과 피드백 학습
- Reward Modeling
- RL 기반 평가 최적화
- Synthetic Feedback 생성

---

# 7. 주요 응용 분야

## 7.1 코드 평가

- 코드 실행 검증
- 테스트 케이스 수행
- 런타임 결과 확인
- 정적 분석
- 보안 취약점 탐지

---

## 7.2 수학 평가

- 계산기 기반 검증
- Symbolic Reasoning
- 정답 유도 과정 검토
- 수식 일관성 확인

---

## 7.3 교육

- 자동 채점
- 에세이 평가
- Rubric 기반 평가
- 피드백 생성
- 학습자별 평가 기준 적용

---

## 7.4 RL 및 Reward Modeling

Agent-as-a-Judge는 강화학습의 보상 생성기로 활용될 수 있다.

구조:

```text
Agent가 행동 수행
  ↓
Judge Agent가 결과 평가
  ↓
Reward 생성
  ↓
Agent 개선
```

---

# 8. 주요 한계

## 8.1 높은 비용

Agentic Evaluation은 여러 단계의 추론과 도구 호출을 포함하므로 비용이 높다.

## 8.2 높은 지연 시간

다중 에이전트 토론, 외부 API 호출, 도구 실행은 응답 지연을 증가시킬 수 있다.

## 8.3 보안 위험

도구를 사용하는 평가 시스템은 다음 위험을 가진다.

- Prompt Injection
- Tool Abuse
- 악성 코드 실행
- 외부 시스템 오남용
- 개인정보 노출

---

# 9. 실무적 의미

AI 시스템이 Agent화될수록 평가 시스템도 Agent화되어야 한다.

기존 구조:

```text
User → LLM → 응답
```

Agent-as-a-Judge 기반 구조:

```text
User
  ↓
Task Agent
  ↓
Judge Agent
  ├─ Search
  ├─ Tool Use
  ├─ Verification
  ├─ Memory
  └─ Multi-Agent Debate
  ↓
최종 응답
```

---

# 10. 핵심 인사이트

이 논문의 핵심은 다음이다.

> 평가가 단순 채점 문제가 아니라, 계획·탐색·검증·협업이 필요한 추론 문제로 바뀌고 있다.

---

# 11. 한 줄 요약

Agent-as-a-Judge는 텍스트를 읽고 점수만 매기는 LLM 평가자를 넘어, 실제 도구와 근거를 활용해 검증 가능한 판단을 수행하는 차세대 AI 평가 시스템이다.
